## 総合評価

今回の修正は、前回の主要な指摘に適切に対応しています。 特に、旧 SDK 互換実装の完全削除、`BundleOutputPlan` の再利用、同一 `generateName` Prefix の複数 Hook のテスト追加は評価できます。

ただし、以下の論点は残っています。

| 優先度 | 項目 | 評価 |

## 1. 修正済みで、これ以上変更する必要がない部分

### 旧 SDK 互換コードの削除

旧 `compat/mcl-v0.4.7`、Build Tags、代替実装、Dockerfile の SDK 切り替え、Release の SDK Matrix が削除されています。

これで、Plugin の依存は基本的に `go.mod` で管理する単一の MCL SDK に統一できました。この方針を維持してください。 旧 SDK のサポートを再導入する必要はありません。

### Phase 出力 Plan の再利用

[internal/plugin/render.go](https://github.com/manifest-configuration-language/argocd-plugin/blob/main/internal/plugin/render.go?utm_source=chatgpt.com) では、Operation ごとに一度 `mcl.NewBundleOutputPlan(bundle)` を生成し、`outputPlan.RenderPhaseArtifacts(phase)` を繰り返し呼び出す構成に変更されています。

これは適切です。同一 Bundle に対して Phase ごとに Scope Index や Lifecycle 情報を作り直す問題を解消しています。

### 同一 Prefix の複数 Hook

MCL SDK の `RenderedArtifact` に `ArtifactID` と `BundleIndex` が追加され、Plugin は `generateName` Hook を Prefix だけで識別しなくなりました。

今回追加された Unit Test は、同じ Prefix の PreSync / PostSync Hook が別々に出力されることを確認しています。

Kind E2E でも、2つの Job の実行、Cleanup、再 Sync で異なる Job が生成されることを検証するようになっています。

前回の「同じ Prefix を持つ2つの Hook が衝突する」具体的な問題は修正されています。 以下で指摘するのは、それとは別の、ArtifactID が取得できない場合の問題です。

### ARM64 ビルド

CI に `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build` が追加されています。

これは通常 CI に追加する検証として十分です。Kind E2E まで ARM64 で実行する必要はありません。

## 2. P1 — ArtifactID が取得できない Hook の重複問題

対象：

- [MCL: internal/output/lifecycle.go](https://github.com/manifest-configuration-language/mcl/blob/28a6104d19080e4dabab6382eba9af5134b9d0b6/internal/output/lifecycle.go?utm_source=chatgpt.com#L420-L440)
- [Plugin: internal/plugin/render.go](https://github.com/manifest-configuration-language/argocd-plugin/blob/b5e074c80d0210fd336a9700e2b6f58d15fe594b/internal/plugin/render.go?utm_source=chatgpt.com#L113-L119)

今回追加された `StableArtifactIDs()` は、Resource の `SourcePath` と `Span` から ID を作成しています。

同じソース位置を持つ Artifact が複数ある場合は、ID を空にします。曖昧な Identity を無理に割り当てないという判断は適切です。

問題は、その後の Plugin 側のフォールバックです。

```
if artifact.ArtifactID != "" {
    resourceID.key += "\x00generated\x00" + artifact.ArtifactID
} else {
    resourceID.key += "\x00generated\x00" +
        operation.name + "\x00artifact-index\x00" +
        strconv.Itoa(artifact.BundleIndex)
}
```

`ArtifactID` がない場合、キーに `operation.name` が含まれます。

つまり、同じ Hook が Create と Update の両方で評価されても、異なるリソースとして出力されます。

例えば、同じ MCL のソース位置からループなどで複数の Job が生成され、そのソース位置が重複して `ArtifactID` が空になった場合です。

|            | Create             | Update             |
| ---------- | ------------------ | ------------------ |
| Artifact A | `create / index 0` | `update / index 0` |
| Artifact B | `create / index 1` | `update / index 1` |

本来2個の Hook でよい場合でも、4個の Hook として出力される可能性があります。

これは現時点ではコード上の条件から導かれるリスクであり、Kind 上での再現確認はまだありません。

推奨修正： MCL SDK 側で、同一ソース位置から展開された複数 Artifact を区別できる識別情報を提供することを検討してください。例えば、ソース位置に加えて、同じ生成箇所からの展開を識別する安定した情報を保持する方法です。

ただし、単に配列 Index を追加するのではなく、Create / Update で順序が変わる場合も考慮する必要があります。Identity を確実に判定できない場合は、誤統合を避ける現在の方針を維持し、制限を明示するのが安全です。

少なくとも、`ArtifactID == ""` のリソースが Create / Update の両方に現れるテストを追加してください。

## 3. P2 — SDK 更新のたびに固定 Lock テストが壊れる

対象：

- [internal/plugin/testdata/mcl-cli-lock/mcl.lock](https://github.com/manifest-configuration-language/argocd-plugin/blob/main/internal/plugin/testdata/mcl-cli-lock/mcl.lock?utm_source=chatgpt.com)
- [internal/plugin/mcl_lock_test.go](https://github.com/manifest-configuration-language/argocd-plugin/blob/main/internal/plugin/mcl_lock_test.go?utm_source=chatgpt.com)

今回、Fixture の `mcl.lock` が次の値に書き換わっています。

```
{
  "toolchain": {
    "mcl": "v0.4.8-0.20261108083610-28a6104d1908",
    "go": "go1.27.3"
  }
}
```

これで今回の SDK とは整合しますが、次の MCL リリースでバージョンを更新すると、同じ問題が再発します。

`TestGenerateUsesMCLToolchainLockAndSharedCache` では、既に MCL SDK を使ってテスト用 Lock を生成しています。

したがって、固定 Fixture を読み込む `TestGenerateLoadsMCLCLIGeneratedLock` を維持する必要性を再評価してください。

CLI 生成 Lock との互換性を検証したいのであれば、テスト対象のバージョンに対応する CLI で Lock を生成するのが理想です。それが過剰であれば、重複するテストを整理してもよいと思います。

最新 SDK に追随するたびに、テストデータのバージョンを手動編集する運用は避けたいです。

## 4. P2 — Release Workflow の再実行が完全には冪等でない

対象：[.github/workflows/release.yml:117–129, 217–237](https://github.com/manifest-configuration-language/argocd-plugin/blob/b5e074c80d0210fd336a9700e2b6f58d15fe594b/.github/workflows/release.yml?utm_source=chatgpt.com)

Release の `bump` と `channel` を MCL 本体と同じ方式に変更した点は適切です。

現在は `patch / minor / major` と `stable / rc` を指定でき、最新の安定版タグから次のバージョンを計算しています。

一方、同じコミットに既存タグがある場合、`prepare` ジョブでは「公開を再開する」と判断します。

```
if [[ -n "$previous" ]]; then
    printf 'Commit %s already has tag %s; resuming publication.\n' \
      "$GITHUB_SHA" "$previous" >&2
    # ...
fi
```

しかし最後の `release` ジョブは、常に以下を実行します。

```
gh release create "${args[@]}"
```

そのため、GitHub Release が既に存在する状態で Workflow を再実行すると、Release 作成が失敗する可能性があります。

推奨： 既存の Release を確認し、すでに正常に公開済みであれば重複作成を避けるようにしてください。未完成の公開を再開する場合は、既存タグ・イメージ・Release の状態が整合していることを確認する必要があります。

なお、このバージョン計算方式は MCL 本体の Release Workflow とほぼ同じです。再利用している仕組みだから正しいとは限らないため、必要であれば MCL 側にも同じ冪等性改善を適用するのがよいです。

## 5. P2 — RC から Stable への遷移を明示的にテストする

現在のバージョン計算方式は概ね妥当です。

特に次のケースは検証しておきたいです。

| 現在の最新 Stable | 操作 | 期待する新規タグ |
| ------------------------ | -------------- | ------------- |
| `v0.1.0` | patch / stable | `v0.1.1` |
| `v0.1.0` | patch / rc | `v0.1.1-rc.1` |
| `v0.1.0` + `v0.1.1-rc.1` | patch / rc | `v0.1.1-rc.2` |
| `v0.1.0` + `v0.1.1-rc.2` | patch / stable | `v0.1.1` |
| `v0.1.0` | minor / stable | `v0.2.0` |

現在のコードからは、この基本的な計算は成立するように見えます。

ただし、RC と Stable が同一コミットを指す場合、既存タグの再利用、途中失敗からの再実行、古いコミットの Release 禁止など、実行状態に依存する分岐が存在します。

この部分は大きな E2E フレームワークを作る必要はありません。バージョン決定ロジックの重要な境界条件を検証できるようにするだけで十分です。

## 6. P3 — ArtifactID の保証範囲を明確にする

対象：[MCL: internal/output/lifecycle.go](https://github.com/manifest-configuration-language/mcl/blob/28a6104d19080e4dabab6382eba9af5134b9d0b6/internal/output/lifecycle.go?utm_source=chatgpt.com)

現在の `ArtifactID` は、ソース位置を SHA-256 でハッシュして生成しています。

この ID は、同じソースと同じ位置で評価された Artifact を識別する用途には適しています。

ただし、ソースの前方にコードを追加すると `Span` が変わる場合があり、チェックアウト先のパスが異なれば `SourcePath` も変わる可能性があります。

したがって、Kubernetes Resource の永続 ID として扱うべきではありません。

今回の Plugin は Manifest 生成中の一時的な統合キーとして使用しているため、現在の用途なら問題ありません。

SDK のコメントやドキュメントで、`ArtifactID` は「同じソース状態における評価間の照合に使う識別子」であり、ソース編集や配置変更を超えて不変ではないことを明示するとよいです。

## 7. SDK のバージョン管理について

今回の最新 Plugin では、`go.mod` が次のバージョンに更新されています。

```
github.com/manifest-configuration-language/mcl
v0.4.8-0.20261108083610-28a6104d1908
```

これは追加 API を含む MCL コミットを指す Go の擬似バージョンです。

したがって、報告されていた「Go workspace なしでは新 API がないためビルドできない」という問題は、GitHub 上の現行コードでは解消に向かっています。実際に最新 CI も成功しています。

ただし、MCL の公開 Release は確認時点で `v0.4.7` が最新でした。

正式な SDK Release を作るのであれば、MCL 本体の変更を安定させて新しいバージョンを公開し、そのタグに Plugin の依存を更新してください。その後、Plugin の通常ビルド・Unit Test・Kind E2E を確認して公開する順序が適切です。

擬似バージョンを使うこと自体は開発中なら問題ありません。ビルド時に `go get` で最新 main を動的取得する方式へ戻す必要はありません。

## 8. 推奨する対応順序

| 優先度 | 対応 | 対象 |
| ----- | ---------------------------------------------- | --------------- |
| P1 | `ArtifactID == ""` 時の複数 Operation 統合を検証・必要なら修正 | MCL + Plugin |
| P2 | 固定バージョンの Lock Fixture を整理 | Plugin |
| P2 | 既存 Release がある場合の再実行を安全にする | Plugin、必要なら MCL |
| P2 | Release の RC / Stable 境界条件を確認 | Plugin |
| P3 | ArtifactID の安定性と用途を文書化 | MCL |
| リリース前 | 正式な MCL SDK タグへ依存を更新し、通常 CI / Kind E2E を確認 | 両方 |

現在の E2E 実行状況は、[こちら](https://github.com/manifest-configuration-language/argocd-plugin/actions/runs/42463774342?utm_source=chatgpt.com) で確認できます。私が確認した時点ではまだ実行中であり、今回変更した複数 Hook の Kind テストが成功したとは断定できません。

結論として、今回の修正でアーキテクチャと保守性はかなり改善されています。 旧 SDK 互換コードを戻す必要はなく、Dockerfile や Release Workflow の基本構成も維持して構いません。

次に優先すべきなのは、ArtifactID を確定できないケースを含めた Hook の同一性の保証と、SDK 更新・Release 再実行時の運用上の不具合をなくすことです。
